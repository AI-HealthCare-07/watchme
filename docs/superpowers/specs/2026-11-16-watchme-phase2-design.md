# Watchme 2단계 설계: 카카오 로그인 + 하루 두 번 카톡 (v0.1)

- 날짜: 2026-11-16
- 앞 문서: `2026-11-13-watchme-design.md`(원래 설계, 7장·4장(가)), `2026-11-16-watchme-redesign-design.md`(1단계 개편, 8장 2단계 메모)
- 현재: 1단계(무료 30일 체험, 초록 디자인, 맞춤 계획, /ready, 주간 PDF, 30일 리포트) 배포 완료 — https://evrd.fyi

## 1. 의도와 이유

- 사용자가 직접 정한 학습 목표: **카카오톡 연동을 실제로 끝까지 경험하기** (로그인 → 동의 → 토큰 보관·갱신 → 서버가 메시지 발송). 기능 수보다 이 흐름을 한 번 제대로 겪는 것이 우선.
- 서비스 쪽 이유:
  - 1단계 약점 "링크를 잃으면 기록도 잃음"을 카카오 로그인으로 해결.
  - 30일 완주를 돕는 넛지. 아침엔 오늘 계획, **저녁엔 "잘 지켰는지" 다시 묻고 기록하게** 한다(사용자: "그래야 저녁에 잘 지켰는지 다시 한 번 확인해서 기록할 거잖아").

## 2. 목표 / 비목표 / 반목표

**목표**
- 카카오 로그인(선택 사항)으로 개인 링크 체험(`/c/<token>`)을 카카오 계정에 연결. 다른 기기에서 "카카오로 이어서 하기"로 내 체험을 다시 찾기.
- "나에게 보내기"로 매일 두 번 메시지: 아침 7:30 오늘 계획, 저녁 21:00 기록 확인. 일요일은 체중 재는 날 안내.
- 체험 1일째부터 연결 가능(30일을 기다리지 않음).
- 30일 리포트의 노란 카드를 "다음 30일 도전하기"로 바꾸고, 새 체험이 같은 카카오 계정에 이어 붙음.
- 알림 끄기, 카카오 연결 끊기(저장한 토큰 즉시 삭제).

**비목표 (이번에 안 함, 3단계 후보)**
- 효도 구독(자녀가 부모 주간 소식 받기). 메모: 자녀도 카카오 로그인 → 자녀 본인의 "나에게 보내기"로 보내면 친구 API 검수 없이 가능. 대신 부모 동의 절차가 새로 필요.
- 결제(실결제는 사업자 필요, 한다면 카카오페이 테스트 결제까지).
- 친구에게 보내기, 카카오 채널·챗봇(원래 설계 B안), 알림톡.
- 알림 시간 사용자 선택, 카톡 안에서 버튼으로 바로 기록.
- 31일째 이후 계획 연장(계획·주차·PDF·리포트가 모두 30일 기준이라 큰 작업).
- 닉네임·이메일·프로필 수집.
- 카카오 "연결 끊기 알림" 웹훅 *(제 판단: 발송 실패 처리로 대신함, 8장)*.

**반목표 (돌아가도 실패)**
- 카카오 토큰을 평문으로 저장하거나, 백업 파일에서 풀 수 있는 형태로 남기기.
- 체험 토큰(`/c/<token>`)을 카카오 쪽 URL·파라미터로 넘기기.
- 하루 두 통보다 많이 보내거나, cron이 두 번 돌았다고 같은 메시지가 두 번 가기.
- 카카오 키가 없는 환경(로컬·테스트)에서 사이트가 깨지기.
- 1단계 원칙 깨기: 외부 스크립트 로드, 로그인 없이 못 쓰는 화면, 지금보다 많은 개인정보 수집, 혼내는 말투.
- 카카오 키·`.env`·`data/raw/` 커밋.

## 3. 제약

- 지금 구조 유지: FastAPI + Jinja2 서버 렌더링, PostgreSQL, Docker Compose, push-to-deploy(`git push evrd main`), 빌드 단계 없음.
- 날짜는 `today_kst()`. 공개 주소는 `PUBLIC_BASE_URL` (redirect_uri와 메시지 링크도 이걸로 만든다).
- **카카오 개발자 콘솔 작업과 키 입력은 사용자가 직접** 한다(9장). 구현 쪽은 키를 보거나 다루지 않는다.
- 운영 DB는 지우지 않는다. 새 표만 추가해서 `create_all`로 생성(기존 표 구조 변경 없음).
- 테스트는 실제 카카오를 부르지 않는다. `.venv/Scripts/python -m pytest -q` (현재 152개 통과)가 계속 통과.

### 카카오 API 사실 (2026-11-16 공식 문서 확인)
- 인가: `GET https://kauth.kakao.com/oauth/authorize` (`client_id`=REST API 키, `redirect_uri`, `response_type=code`, `state`, `scope`).
- 토큰: `POST https://kauth.kakao.com/oauth/token` (`grant_type=authorization_code`, `client_id`, `redirect_uri`, `code`, `client_secret` — 시크릿 ON이면 필수). 응답 `access_token`, `refresh_token`, `expires_in`(예시 약 12시간), `refresh_token_expires_in`(예시 60일), `scope`.
- 갱신: 같은 엔드포인트 `grant_type=refresh_token`. **리프레시 토큰 남은 기간이 1개월 미만일 때만 새 refresh_token이 응답에 들어옴** → 들어오면 바꿔 저장.
- 회원번호: `GET https://kapi.kakao.com/v2/user/me`의 `id`(항상 포함, 동의 불필요).
- 나에게 보내기: `POST https://kapi.kakao.com/v2/api/talk/memo/default/send`, `template_object`(JSON, 텍스트형 등), 동의항목 `talk_message` 필요. 나에게 보내기는 검수·발송 제한 없음(개발자 포럼 답변).
- 연결 끊기: `POST https://kapi.kakao.com/v1/user/unlink` (액세스 토큰) → 동의 철회 + 토큰 폐기.
- **알림 주의**: "나와의 채팅"은 메모용이라 **푸시 알림이 안 울릴 가능성이 높다**(개발자 포럼). 9장의 첫 실험에서 사용자 폰으로 확인. 안 울려도 설계는 그대로, 문구만 "카톡 열면 오늘 계획이 와 있어요" 쪽으로.

## 4. 접근 방식 (검토한 안과 선택)

| 결정 | 검토한 안 | 선택 (이유) |
|---|---|---|
| 2단계 범위 | 1. 나 혼자 루프 / 2. + 효도 구독(결제 없음) / 3. + 카카오페이 테스트 결제 | **1** (사용자 선택). 학습 목표를 다 채우면서 가장 작음. 2·3은 비목표에 메모. |
| 하루 메시지 | A. 아침만 / B. 아침 + 미기록일만 저녁 / C. 아침 + 저녁 매일 | **C** (사용자 선택). 저녁에 잘 지켰는지 다시 확인하고 기록하게. |
| 30일 뒤 | A. 리포트에서 다음 30일 도전(새 체험, 같은 계정) / B. 31일째부터 계속 | **A** (사용자 선택). 지금 시작 흐름 재사용, 나중에 유료를 붙이면 이 버튼 자리가 결제 자리. |
| 로그인 구현 | 1. OAuth를 서버에서 직접 호출(httpx) + 세션 없음 / 2. Authlib 등 라이브러리 + 세션 / 3. 카카오 JS SDK | **1** (사용자 선택). 카카오 흐름이 코드에 그대로 보여 학습 목표에 맞음. 2는 과정이 숨고 1단계에 없던 세션이 생김. 3은 외부 스크립트 금지에 걸리고 서버 발송엔 어차피 서버 토큰이 필요. |
| 발송 시점 | 서버 cron + 스크립트 / 앱 안 스케줄러 | **cron** *(제 판단)*. purge와 같은 검증된 방식. 앱 안 스케줄러는 재시작·배포 때 빠지거나 겹침. |
| 토큰 보관 | 평문 / 암호화(`cryptography` Fernet, 키는 서버 `.env`) | **암호화** *(제 판단)*. PC로 복사되는 `pg_dump` 백업에 토큰이 있어도 풀 수 없게. |
| DB 변경 | `trials`에 컬럼 추가(운영 표 DROP 필요) / 새 표만 추가 | **새 표만** *(제 판단)*. `create_all`로 생성, 운영 데이터 유지. |

## 5. 화면과 흐름

```
[/ready] 또는 [기록 화면]  "카톡으로 알림 받기" ─┐
[시작 화면]               "카카오로 이어서 하기" ─┼→ 카카오 로그인·동의 → 콜백
                                                  │    ├ 체험에서 왔으면: 그 체험 연결 → 환영 메시지 1통 → /c/<token>
                                                  │    └ 시작 화면에서 왔으면: 계정의 가장 최근 체험 /c/<token> (없으면 안내)
[매일 7:30]  아침 메시지 ── [오늘 계획 보기] → /c/<token>
[매일 21:00] 저녁 메시지 ── [기록하기]      → /c/<token>
[31일째 아침] "30일 완주! 리포트가 나왔어요" ── [리포트 보기] → /c/<token>/report → 발송 멈춤
[리포트] "다음 30일 도전하기" → 새 체험(같은 계정에 연결) → 새 체험의 /ready
```

### 5.1 연결 버튼 위치
- **/ready**: 주 버튼(Day 1 시작) 위에 노란 카드 "카톡으로 아침 계획·저녁 체크 받기 [카카오로 연결]". 연결 안 해도 그대로 진행 가능.
- **기록 화면**: 연결 안 됐으면 작은 카드로 같은 버튼. 연결됐으면 작은 줄 "💬 카톡 알림 켜짐 · [끄기] · [연결 끊기]".
- **시작 화면**: 아래쪽 보조 링크 "이미 하고 있나요? 카카오로 이어서 하기".
- **리포트**: 노란 카드를 "다음 30일 도전하기"로 교체(연결 여부와 관계없이 보임). 연결된 체험이면 "새 도전도 카톡으로 이어서 알려 드려요" 한 줄.
- 카카오 키가 설정되지 않은 환경에서는 카카오 관련 버튼·카드를 숨긴다(리포트의 "다음 30일 도전하기"는 남김).

### 5.2 로그인·연결 규칙
- 동의항목은 **`talk_message`만** 요청. 회원번호(`id`)만 저장, 닉네임·이메일 없음.
- `state`: 요청마다 새 무작위 값. 어떤 체험에서 왔는지는 **`state`와 함께 서버가 서명한 짧은 쿠키**(HttpOnly, Secure, SameSite=Lax, 10분)에 담고, 카카오로 가는 URL엔 체험 토큰을 넣지 않는다. 콜백에서 `state` 불일치·쿠키 없음 → 안내 화면.
- 동의 화면에서 아예 취소(콜백에 `error=access_denied`, code 없음) → 연결 없이 원래 화면(체험에서 왔으면 `/c/<token>`, 아니면 시작 화면)으로 돌아가 "연결을 취소했어요" 안내.
- 로그인은 했지만 `talk_message`만 동의 안 함(토큰 응답 `scope`에 없음) → 연결은 하되 "메시지 동의가 없어서 알림을 보낼 수 없어요 [다시 동의하기]" 표시.
- 한 체험은 한 카카오 계정에만 연결. 이미 **다른** 계정에 연결된 체험이면 거절하고 안내 *(제 판단)*. 같은 계정이면 그냥 통과(토큰만 갱신).
- 한 계정에 체험 여러 개 가능(다음 도전). 발송 대상은 그 계정의 "진행 중" 체험(아래) 하나.
- 연결 직후 환영 메시지 1통("연결됐어요. 아침 7:30엔 오늘 계획, 저녁 9시엔 기록 확인을 보내 드릴게요") — 사용자가 바로 확인할 수 있고, 첫 실험(알림 여부)도 이걸로 한다. 연결한 날 저녁 21:00 메시지도 조건대로 나간다(문구가 "내일부터"가 아닌 이유). 환영 메시지는 체험에서 연결했고 그 체험이 진행 중(n = 1~30)일 때만.
- 기록 화면의 연결 카드는 n ≤ 30일 때만 보인다 *(제 판단: 끝난 체험엔 보낼 메시지가 없음)*. 끝난 체험은 리포트의 "다음 30일 도전하기"로.
- "가장 최근 체험" = `trials.created_at`이 가장 늦은 것 *(제 판단)*.

### 5.3 다음 30일 도전
- 리포트(31일째 이후)에서만, POST + 요청 제한. 한 체험에서 한 번만 *(빌더가 방식 결정)*.
- 새 체험: 성별·나이·키는 그대로, 몸무게는 마지막 체중 기록(없으면 시작 몸무게), 시작일은 오늘. 맞춤 답변 5개도 복사 *(제 판단: 바로 시작하게. 바꾸고 싶은 답은 이번엔 지원 안 함)*. 계획 종류(variant)는 새 몸무게로 다시 정함.
- 이전 체험이 카카오에 연결돼 있으면 새 체험도 같은 계정에 연결. 이동: 새 체험의 /ready.

## 6. 메시지

모두 텍스트형 템플릿, 버튼 하나, 링크는 `PUBLIC_BASE_URL` 기준. 텍스트 길이 제한(텍스트형 약 200자)을 넘지 않게 빌더가 줄임 규칙을 정함.

**진행 중 체험** = 계정에 연결된 체험 중 `setup_done`이고 시작일 기준 날짜 `n = (오늘 - 시작일) + 1`이 1~31인 가장 최근 체험. (`current_day`는 1~30으로 자르므로 발송엔 자르지 않은 값을 쓴다.)

| 때 | 조건 | 내용 | 버튼 |
|---|---|---|---|
| 아침 7:30 | n = 1~30 | "Day n · 오늘 계획" + 아침·점심·저녁·운동 한 줄씩(이모지). 자유 한 끼 날은 저녁 줄이 "자유 한 끼 🎉". 일요일은 "오늘은 체중 재는 날이에요 ⚖️" 한 줄 추가. | 오늘 계획 보기 → `/c/<token>` |
| 저녁 21:00 | n = 1~30, 오늘 기록 없음 | "오늘 잘 지키셨나요? 10초면 기록돼요." 일요일은 "체중도 같이 적어 주세요." | 기록하기 → `/c/<token>` |
| 저녁 21:00 | n = 1~30, 오늘 기록 있음 | "오늘 기록 고마워요. 바꿀 게 있으면 눌러 주세요." | 기록 보기 → `/c/<token>` |
| 저녁 추가 줄 | n = 7·14·21·28 | "이번 주 요약이 나왔어요. 다음 주 강도도 골라 주세요." | (같은 버튼) |
| 31일째 아침 | n = 31 | "30일 완주! 리포트가 나왔어요 🎉" | 리포트 보기 → `/c/<token>/report` |

- 리포트는 `days_left`가 0이 되는 31일째부터 열리므로, 30일째 저녁이 아니라 **31일째 아침**에 보낸다. 그 뒤 그 체험으론 발송 없음.
- 계획 내용은 기록 화면과 같은 `build_plan(...)` 결과를 쓴다(강도 단계 반영).
- 일요일 저녁 기록 화면에선 체중 칸을 눈에 띄게(빌더가 방법 결정).
- 문구는 1단계처럼 친근한 존댓말, 혼내지 않기.

## 7. 데이터 (새 표 3개, 기존 표 변경 없음)

- **kakao_accounts**: `kakao_id`(회원번호, PK), `refresh_token_enc`(Fernet 암호문, 없으면 NULL), `can_message`(talk_message 동의 + 토큰 유효), `notify`(사용자가 켠/끈 상태, 기본 켬), `created_at`.
- **trial_owners**: `token`(PK, FK trials, ON DELETE CASCADE), `kakao_id`(FK kakao_accounts).
- **sent_messages**: (`kakao_id`, `date`, `kind`) 복합 PK, `kind` ∈ morning/evening/report/welcome. 중복 발송 방지.
- 액세스 토큰은 저장하지 않는다 *(제 판단)*: 발송할 때마다 리프레시 토큰으로 새로 받음(하루 2번 × 사용자 수라 부담 없음). 갱신 응답에 새 refresh_token이 있으면 바꿔 저장 → 매일 쓰는 동안은 만료되지 않음.
- **보관·삭제** (`purge_expired` 확장): 체험이 지워지면 `trial_owners`도 지워지고, 남은 체험이 없는 계정은 계정 행(토큰 포함)과 `sent_messages`도 삭제. `sent_messages`는 오래된 행(예: 40일 지난 것) 정리.
- **개인정보 안내** 갱신: 시작 화면 수집 항목에 "카카오로 연결하면 카카오 회원번호와 메시지 발송 권한(암호화 보관)을 저장해요. 연결을 끊으면 바로 지워요" 추가.

## 8. 발송·오류 처리

- `scripts/send.py`: `python -m scripts.send morning|evening`. 서버 cron(KST): `30 7 * * *` morning(31일째 리포트 메시지 포함), `0 21 * * *` evening. 실행 방식은 purge와 같게(`docker compose exec -T app ...`, 로그는 `~/send.log`, 보낸 수·실패 수 한 줄).
- 대상: `notify` 켬 + `can_message` + 진행 중 체험 있음.
- 순서: `sent_messages`에 (계정, 오늘, 종류) 먼저 기록(이미 있으면 건너뜀) → 토큰 갱신 → 발송. 실패해도 그 날 그 종류는 다시 보내지 않음 *(제 판단: 최대 한 번. 알림이 두 번 가는 것보다 한 번 빠지는 게 낫다)*.
- 토큰 무효·동의 철회(카카오가 사용자 연결 끊기 등) 응답 → `can_message = false`, 토큰 삭제. 기록 화면에선 "카톡 연결이 끊겼어요 [다시 연결]". 연결 끊기 웹훅을 따로 받지 않는 대신 이걸로 처리.
- 기타 오류(네트워크·5xx)는 로그만 남기고 다음 사람으로. 재시도 없음.
- **연결 끊기 버튼**: 카카오 unlink 호출(실패해도 진행) → 계정 행·연결 삭제. 체험과 기록은 링크로 계속 사용 가능.
- **알림 끄기**: `notify = false`만. 다시 켜기 버튼.
- 카카오 HTTP 호출은 한 모듈(`app/kakao.py` 등)에 모으고, `httpx` 클라이언트를 바꿔 끼울 수 있게 해서 테스트에서 `httpx.MockTransport`로 대신한다. `httpx`를 운영 의존성으로, `cryptography` 추가.
- 환경변수: `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`(사용자가 입력), `TOKEN_KEY`(Fernet 키, 서버에서 무작위 생성해 `.env`에만 — 출력·커밋하지 않음). `.env.example`엔 이름만.
- 요청 제한: 로그인 시작(`/auth/kakao`)과 다음 도전 생성에 IP별 제한(기존 `RateLimiter`).

## 9. 사용자가 할 일 (카카오 개발자 콘솔)과 첫 실험

1. developers.kakao.com에서 앱 만들기.
2. 카카오 로그인 활성화. Redirect URI 등록: `https://evrd.fyi/auth/kakao/callback` (로컬 시험용 `http://localhost:8000/auth/kakao/callback`도). 경로 이름은 빌더가 바꾸면 여기도 같이.
3. 플랫폼 → Web 사이트 도메인 `https://evrd.fyi` (+ `http://localhost:8000`).
4. 동의항목: "카카오톡 메시지 전송(talk_message)"만 선택 동의로. 닉네임 등은 사용 안 함.
5. 클라이언트 시크릿 켜기. REST API 키와 시크릿을 서버 `.env`에 직접 입력(권한 600).
6. (허용 IP 설정이 보이면) 서버 공인 IP 허용 또는 비워 두기.

**첫 실험(구현 첫 단계)**: 로그인 → 콜백 → 환영 메시지 1통까지만 먼저 만들어 배포 → 사용자 폰으로 연결 → ① 메시지 도착, ② 푸시 알림이 울리는지, ③ 버튼 링크가 열리는지 확인하고 결과를 runbook에 기록. 알림이 안 울리면 6장 문구만 조정.

## 10. 성공 기준

- 사용자가 자기 폰에서 카카오로 연결하고, 다음 날 아침·저녁 메시지를 받고, 버튼으로 기록 화면에 들어가 10초 안에 기록한다.
- 다른 기기(또는 시크릿 창)에서 "카카오로 이어서 하기"로 같은 체험이 열린다.
- cron을 같은 시각에 두 번 돌려도 메시지는 한 번만 간다.
- 연결 끊기 후 DB에 그 사용자의 토큰이 없다. 백업 파일만으로는 토큰을 풀 수 없다.
- 카카오 키가 없는 로컬·테스트에서도 1단계 흐름이 그대로 동작하고 전체 테스트가 통과한다.
- runbook에 카카오 앱 설정, `.env` 항목, cron 등록, 첫 실험 결과가 기록돼 있다.

## 11. 빌더에게 맡기는 것

- URL 이름(콜백·연결 끊기·알림 끄기·다음 도전), 모듈·템플릿 구성.
- `state` 쿠키 서명 방식(표준 라이브러리 `hmac` 등, 키는 `TOKEN_KEY`에서 파생 가능), 쿠키 이름.
- 메시지 문구 세부와 200자 줄임 규칙, 일요일 저녁 체중 칸 강조 방법.
- 다음 도전 "한 번만" 보장 방식.
- 카카오 오류 코드별 분기(무효 토큰·동의 없음 vs 기타) — 실제 응답은 첫 실험에서 확인.
- 테스트 구성(TDD, 카카오는 MockTransport, 발송 대상 날짜 경계 n=0·1·30·31·32, 중복 발송, 키 없을 때 숨김).
- 배포 순서: 새 의존성·환경변수 추가 → `TOKEN_KEY` 생성 → 배포(`create_all`이 새 표 생성) → cron 등록(사용자 승인 후, purge와 같이).
